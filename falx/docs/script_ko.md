## [00:40] 01 Problem — 같은 데이터, 새 차트, 새 테이블 (1분 40초)

[클릭: Scatter (Figure 1)]

먼저 문제의식부터 말씀드리겠습니다. 이건 논문 Figure 1의 데이터 네 줄입니다. 날짜, 온도, 그리고 그 온도가 최저인지 최고인지를 나타내는 Type 열이 있습니다.

ggplot2나 Vega-Lite 같은 grammar of graphics에서는 차트를 "마크 하나 더하기, 열을 채널에 연결하는 것"으로 정의합니다. 그래서 산점도는 바로 그려집니다. Date를 x에, Temp를 y에, Type을 색에 연결하면 끝입니다. 아래 체크 두 개가 모두 통과하는 게 보이실 겁니다.

[클릭: Floating bars (Figure 2)]

그런데 디자인을 조금만 바꿔서, 하루에 막대 하나씩, 최저에서 최고까지 이어지는 floating bar를 그리고 싶다고 해 보겠습니다. 그러면 y최소값에 Low를, y최대값에 High를 연결해야 하는데요. 문제는 Low와 High가 열이 아니라 Type 열 안에 들어 있는 "값"이라는 점입니다. 체크가 둘 다 실패하고, 차트를 그릴 방법이 없습니다.

[클릭: Reshape with pivot_wider]

그래서 테이블을 pivot_wider로 넓게 바꿔야 비로소 차트가 그려집니다. 차트는 조금 바뀌었는데, 데이터 구조는 완전히 바뀌어야 했다는 것, 이게 이 논문의 출발점입니다.

## [02:20] 01 Problem — 분석가의 노력이 레이아웃에 쓰인다 (1분)

[스크롤: "Analysts spend their effort on layout"]

저자들은 이런 불일치가 일상적으로 생기는 이유를 세 가지로 듭니다. 데이터가 오는 출처마다 레이아웃이 다르고, 분석 과제가 바뀌면 디자인이 바뀌고, 평균이나 누적합, 차이 같은 파생값은 그리기 전에 계산해야 합니다.

그래서 지금 분석가는 아래 네 상자를 다 거쳐야 합니다. 목표 테이블을 머릿속에 그리고, pivot_longer나 mutate 같은 함수 이름을 떠올리고, 변환 코드를 쓴 다음에야 열을 채널에 연결할 수 있습니다. Falx의 목표는 앞의 세 상자를 없애는 것입니다.

그래서 연구 질문은 이렇습니다. 사용자가 시각화를 예시로 명세하고, 데이터 변환은 프로그램 합성기에 맡길 수 있는가. 여기서 중요한 점은 예시가 "열"이 아니라 "값"에 대한 진술이라는 겁니다. 이 막대는 62.7에서 시작해서 63.4에서 끝난다는 식으로요. 그래서 사용자는 아직 존재하지 않는 열의 이름을 몰라도 됩니다.

## [03:20] 02 Related work — Falx는 어디에 있나 (1분 40초)

[화면: "Where does Falx sit?" 다이어그램]

관련 연구에서 Falx의 위치를 보겠습니다. 저는 기존 도구들을 하나의 질문으로 비교해 봤습니다. 데이터 레이아웃 작업을 누가 하고, 사용자는 무엇을 적어야 하는가입니다.

[클릭: Data transformation tools]

tidyverse나 Wrangler 같은 변환 도구는 사용자가 직접 변환 단계를 씁니다. 목표 레이아웃을 이미 알고 있어야 합니다.

[클릭: Table synthesizers]

Morpheus나 Scythe 같은 테이블 합성기는 합성기가 변환을 대신 찾아 주지만, 입력은 "출력 테이블의 예시"입니다. 결국 사용자가 목표 테이블을 그려야 하는데, 이게 바로 Falx가 가장 어렵다고 지적한 단계입니다.

[클릭: Grammars of graphics → Design automation]

ggplot2나 Vega-Lite는 테이블이 이미 맞아야 하고, Draco나 Voyager 같은 설계 자동화 도구는 고정된 레이아웃 위에서 "어떤 차트를 그릴지"를 추천합니다. 어떻게 데이터를 그 모양으로 만들지는 다루지 않습니다.

[클릭: Falx]

Falx는 이 둘을 합칩니다. 레이아웃 작업은 합성기가 하고, 사용자는 차트 공간에서 값 몇 개로 예시를 그립니다. 그래서 Falx를 "테이블이 아니라 차트 쪽에서 명세하는 합성기"라고 정리할 수 있을 것 같습니다.

덧붙이면, 저자들은 합성기를 공간을 탐색하는 도구와 이미 정한 디자인을 구현하는 도구로 나누는데, Falx는 구현 도구이면서 결과를 고를 때는 탐색 인터페이스를 빌려 온다는 점이 특징입니다.

## [05:00] 03 Scenario — Eunice는 R로 만든다 (2분 20초)

이제 논문의 사용 시나리오를 따라가 보겠습니다. 목표 차트는 Figure 3입니다. 뉴욕과 샌프란시스코의 기온을 계단 선으로 그리고, 날마다 두 도시의 차이를 색으로 칠한 막대를 얹은 차트입니다.

논문은 먼저 숙련된 분석가 Eunice가 R로 이걸 만드는 과정을 보여주는데요. 오른쪽은 논문에 실린 코드를 Falx 저장소에 들어 있는 같은 날씨 데이터 83행에 대해 실제 R로 돌린 결과입니다. [라이브] 지금은 제 노트북의 R에서 바로 실행됩니다.

[클릭: 3 · Difference bars → As printed]

세 번째, 차이 막대입니다. 인쇄된 코드는 `xmin`과 `xmax`가 모두 Date라서 폭이 0인 사각형이 그려지고, 결과적으로 아무것도 보이지 않습니다. [클릭: Runs as intended] 날짜 앞뒤로 폭을 주면 막대가 보입니다.

[클릭: 4 · Combine]

마지막으로 두 레이어를 합치고 계단 선으로 바꾸면 Figure 3이 됩니다.

[클릭: Novice detours → geom_bar]

제가 생각했을 때 인쇄된 코드의 오류 자체는 단순한 오타입니다. 그림은 분명히 고친 코드로 만들어졌으니까요. 다만 이 오류들이 보여주는 건, 이 경로가 정확한 API 지식을 얼마나 많이 전제하는지입니다.

## [10:00] 04 Falx — 모호함은 코딩이 아니라 보는 것으로 푼다 (1분 30초)

[스크롤: "Ambiguity is resolved by looking"]

그런데 왜 12개나 나왔을까요. 논문은 이 예시에서 후보 8개가 약 9초 만에 나왔다고 보고하는데, 공개된 코드를 실제로 돌려 보면 12개가 나옵니다.

후보 프로그램을 보면 이유가 보입니다. 예시 막대가 첫 번째 날짜에 있는데, 첫 날짜에서는 누적합이 원래 값과 같습니다. 그래서 그 한 행만으로는 "뉴욕 기온"과 "뉴욕 기온의 누적합"을 구별할 수 없습니다. 2번, 4번처럼 막대가 하늘로 치솟는 후보들이 바로 누적합 버전입니다.

[클릭: + second bar]

그래서 두 번째 막대를 2011-10-05에 하나 더 주면 후보가 7개로 줄어듭니다. 남은 여섯 개는 "그룹별 누적합"을 쓰는 프로그램인데, 온도 값이 반복되는 날에만 다르기 때문에 83일 중 3일에서 24일만 차이가 납니다. 눈으로는 거의 구분이 안 됩니다.

[클릭: Line color left blank]

참고로 선의 색을 비워 두면 후보가 24개로 늘어납니다. 예시를 얼마나 구체적으로 주느냐가 탐색 공간을 직접 바꾸는 겁니다.

제가 생각했을 때는 예시 행을 무엇으로 고르느냐가 탐색을 크게 바꾸고, 첫 번째 행은 누적 계산에 대해 최악의 선택입니다. 인터페이스가 "첫 행 예시로는 누적합을 배제할 수 없습니다" 정도의 힌트만 줘도 탐색 한 번을 아낄 수 있을 것 같습니다. 이건 논문의 주장이 아니라 실행 결과를 보고 제가 추론한 내용입니다.

## [12:20] 05 Architecture — 역컴파일, 탐색, 컴파일 (2분 30초)

[화면: "Inside one synthesis run"]

이제 Falx가 내부에서 어떻게 동작하는지 보겠습니다. 한 번의 합성은 세 단계로 이루어집니다.

[클릭: 1 · Decompile]

첫째, 시각화 역컴파일입니다. Falx는 예시를 마크 종류별로 묶어서 레이어를 만들고, 각 레이어를 "차트 프로그램 더하기 예시 테이블"로 바꿉니다. 막대 레이어는 `Bar(x → C1, y → C2, y2 → C3, color → C4)`라는 프로그램과, 2011-10-01, 62.7, 63.4, 0.7이라는 한 줄짜리 예시 테이블이 됩니다. 이 표는 제가 만든 게 아니라 Falx가 실행 중에 찍은 로그에서 그대로 가져온 것입니다.

여기서 핵심적인 환원이 일어납니다. 차트가 고정되고 나면, 시각화 문제는 테이블 문제가 됩니다. 입력 테이블에 어떤 프로그램 P를 적용했을 때 예시 테이블 T가 그 결과 안에 포함되도록 하는 P를 찾는 문제입니다.

[클릭: 2 · Search → Replay the search]

둘째, 데이터 변환 합성입니다. 이건 막대 레이어에 대한 Falx의 실제 탐색 로그를 재생한 것입니다. Falx는 인자가 비어 있는 프로그램 스케치를 펼치면서 탐색하는데, 이 실행에서는 스케치 52개를 펼쳤고, 그중 11개는 인자를 하나도 채우기 전에 버려졌습니다.

왜 이게 가능하냐면, 부분 프로그램 하나가 수십 개의 구체적인 프로그램을 대표하기 때문에, 추상 해석으로 "이 가지에서는 절대 열 네 개짜리 테이블이 나올 수 없다"는 걸 미리 알면 가지 전체를 잘라낼 수 있기 때문입니다. 이게 저자들이 연역적 가지치기를 쓴 이유입니다.

[클릭: 3 · Check T ⊆ P(T_in) → mutate(I, NY − SF)]

셋째 단계로 가기 전에, 포함 관계 검사를 숫자로 보겠습니다. 뉴욕 빼기 샌프란시스코를 계산하면 첫 행이 예시와 정확히 일치합니다.

[클릭: cumsum(I, NY) then mutate]

그런데 누적합 프로그램도 첫 행에서는 통과합니다. 첫 날의 누적합은 원래 값과 같으니까요. 앞에서 본 모호함이 바로 여기서 생깁니다. 반면 [클릭: mutate(I, NY + SF)] 더하기 프로그램은 일치하는 행이 없어서 바로 버려집니다.

[클릭: 4 · Compile]

마지막으로 프로그램 생성 단계에서는 테이블 프로그램과 차트 프로그램을 짝지어 Vega-Lite나 R로 컴파일하고, 중복을 지운 뒤 프로그램이 간단한 순서로 정렬합니다. 응답성을 위해 5초 제한과 20초 제한의 스레드 두 개를 병렬로 돌린다는 점도 논문에 나와 있습니다.

## [16:20] 07 Results — 변환이 어려운 곳에서 가장 큰 차이 (1분 40초)

## [20:10] 10 Critical reflections ① — 예시는 여전히 답의 한 행을 담고 있다 (1분 20초)

[화면: "An example still carries one row of the answer"]

이제 제 관점의 비판입니다. 첫 번째는, 예시가 여전히 답의 한 행을 담고 있다는 점입니다. Amelia가 막대 색에 넣은 0.7은 2011-10-01의 뉴욕 빼기 샌프란시스코입니다. Falx가 일반화하기 전에 사용자가 그 값을 직접 계산해야 합니다.

[클릭: 0.8 · typo]

이 숫자 하나를 0.8로 잘못 넣으면, Falx는 20초 예산 안에 아무것도 찾지 못합니다. 그리고 왜 실패했는지 아무 말도 해 주지 않습니다.

[클릭: 1.011 · NY ÷ SF]

비율을 넣어도 마찬가지입니다. Falx 문법의 mutate는 더하기와 빼기만 지원하기 때문입니다.

그래서 제 생각에는, 예시 방식은 산술을 숨기지만 없애지는 않습니다. 폭포 차트처럼 누적합이 필요한 과제가 Falx 집단에서도 가장 낮은 68.8%였던 이유가 여기에 있을 수 있다고 봅니다. 대안으로는 허용 오차를 두고 탐색해서 "가장 가까운 프로그램은 뉴욕 빼기 샌프란시스코 0.7인데, 0.8을 입력하셨습니다"처럼 알려주거나, 논문의 참가자 F16이 원했던 것처럼 한 필드에 수식을 직접 쓸 수 있게 하는 방법이 있을 것 같습니다. 이건 사용자로 검증된 결과가 아니라 실행 결과를 보고 세운 가설입니다.

## [21:30] 10 Critical reflections ② — 베이스라인은 API 회상을 잰다 (1분)

[스크롤]

두 번째는 베이스라인입니다. 이 연구는 2020년 방식의 R, 그러니까 문서를 검색해서 맞는 함수를 찾는 R과 비교합니다. 실제로 R 집단의 주된 실패 원인은 폭포 차트에 geom_rect를 써야 한다는 걸 모르는 것, 즉 함수 이름이었습니다. 이건 실제 장벽이지만, Falx가 스스로 목표로 내건 "레이아웃을 머릿속에 그리는 어려움"과는 다른 장벽입니다.

그래서 저라면 오른쪽 표처럼 설계를 바꿔 볼 것 같습니다. 참가자 내 설계로 도구 효과와 모집 차이를 분리하고, 문법 밖의 과제를 하나 넣어서 각 도구가 어떻게 실패하는지 보고, 코드 어시스턴트를 쓰는 R을 세 번째 조건으로 넣어 함수 회상이 여전히 병목인지 확인하고, 혼합효과 모형의 추정치를 보고하는 겁니다.

## [22:30] 10 Critical reflections ③ — 논문을 다시 돌려 보기 (1분)

[화면: Paper versus re-run 표]

마지막으로 재현 가능성입니다. 저는 논문의 양쪽을 모두 실제로 돌려 봤습니다. R 쪽은 앞에서 보신 것처럼 인쇄된 코드 세 군데가 의도대로 동작하지 않았습니다.

Falx 쪽은 공개 저장소가 지금의 파이썬에서는 import 단계에서 실패하고, 2020년 당시 환경인 Python 3.8과 pandas 1.1로 맞춰야 돌아갑니다. 그렇게 돌리면 결과는 논문과 가깝지만 같지는 않습니다. 선 예시에서 논문은 후보 2개라고 했는데, 색을 New York으로 지정하면 1개, 색을 비우면 논문처럼 2개가 나옵니다. 선과 막대에서는 논문의 8개 대신 12개가 나옵니다. 논문이 이 수치를 낸 솔버 설정을 밝히지 않아서 정확한 재현은 어렵습니다. 그리고 Figure 2의 막대 하나짜리 예시는 공개 코드에서 오류로 멈춥니다. 작은 버그지만, 사용자가 실제로 마주칠 "조용한 실패"의 예입니다.

그래서 이 발표 자료는 Python 3.8 환경을 고정한 실행 스크립트와 함께 저장소에 올려 두었고, 버튼 하나로 Falx와 R을 실제로 실행할 수 있게 만들었습니다.

## 예상 질문과 답변

**Q1. 예시를 어떤 값으로 줘야 하는지 사용자가 어떻게 아나요? 결국 데이터를 이해해야 하는 것 아닌가요?**
네, 맞습니다. Falx는 열 이름이나 함수는 몰라도 되지만, 예시 한 행의 값은 알아야 합니다. 막대 색 0.7처럼 파생값이면 직접 계산해야 하고요(4.5.1절에 참가자들이 "언제 값을 쓰는지" 헷갈렸다는 언급이 있습니다). 그래서 제 비판 ①에서 수식 입력이나 근사 매칭을 제안했습니다.

**Q2. 후보가 많아지면 오히려 더 어렵지 않나요?**
실제로 선 색을 비우면 24개까지 늘어납니다. 논문은 이를 탐색 패널과 프로그램 복잡도 순 정렬로 다루고, 참가자들이 네 단계로 거르는 전략을 썼다고 보고합니다(4.5.2절). 다만 8번, 9번처럼 3일만 다른 후보는 눈으로 구별이 안 돼서, 저자들도 향후 과제로 "후보 간 차이를 요약해서 보여주기"를 들고 있습니다.

**Q3. 왜 CNN이나 LLM 같은 학습 기반이 아니라 열거 탐색을 썼나요?**
Falx의 목표는 사용자 예시를 반드시 포함하는 프로그램, 즉 정확성이 검증되는 결과입니다. 열거 탐색과 추상 해석은 T ⊆ P(T_in)을 만족하는 프로그램만 내놓기 때문에 예시와 모순되는 결과가 나오지 않습니다. 한 번 합성에 3–20초라는 응답 시간도 이 방식으로 확보했다고 설명합니다(2.2절, 3.2절).

**Q4. 완료율이 넷 중 하나만 유의한데 Falx가 낫다고 말할 수 있나요?**
논문의 주장은 "변환이 어려운 과제에서 효과가 크다"는 쪽이 더 정확합니다. 자동차 판매에서 완료율 68.8% 대 29.4%(p<0.05), 시간 715초 대 1473초(p<0.01)로 효과가 큽니다. 나머지 과제는 유의하지 않고, 집단당 16–17명이며 혼합효과 모형의 추정치가 보고되지 않았다는 점에서 일반화에는 조심해야 한다고 봅니다.

**Q5. 데모의 결과는 진짜 Falx 결과인가요?**
네. 저자 저장소(Mestway/falx, 커밋 fcae5e5)의 코드를 그대로 쓰고, 서버 응답 형식만 맞추는 얇은 래퍼를 붙였습니다. 로컬 서버를 켜면 화면에서 만든 아무 예시나 실시간으로 합성하고, 서버가 없을 때는 같은 코드로 미리 실행해 둔 결과를 재생하며, 화면에 어느 쪽인지 표시됩니다. 예외는 Program viewer의 tidyverse 코드로, 이건 Falx DSL을 제가 기계적으로 옮긴 것이라고 표시해 두었습니다.

**Q6. 왜 논문 수치(8개, 9초)와 재현 결과(12개, 7.6초)가 다른가요?**
논문은 해당 수치를 낸 솔버 설정(스레드, 시간 제한, 스케치 수)과 버전을 밝히지 않았습니다. 저는 공개 서버의 heavy 설정(20초, 스케치 5개)으로 한 번 실행했고, 클라우드 환경의 벽시계 시간입니다. 실행 환경과 설정 차이로 보는 게 합리적입니다.

**Q7. LQ²나 다른 자동화 연구와 무엇이 다른가요?**
Draco, Voyager 같은 설계 자동화는 고정된 레이아웃 위에서 "무엇을 그릴지"를 추천하고, LQ²는 데이터와 차트 유형이 정해진 뒤 막대 폭이나 가로세로비 같은 시각 스타일을 사람의 선호로 최적화합니다. Falx는 그보다 앞단에서, 정해진 디자인에 맞게 데이터를 변환하는 일을 자동화합니다. 저자들도 설계 탐색 도구와 결합하면 레이아웃 제약 없는 탐색이 가능하다고 제안합니다(6절). [확장 항목 확정 후 수업 내용과 연결해 보강]

**Q8. 예시를 하나 더 주는 것과 후보에서 고르는 것 중 무엇이 나은가요?**
논문 참가자는 두 전략을 모두 썼습니다. 처음엔 적게 주고 후보가 많으면 추가하는 사람이 8명, 처음부터 여러 개를 주는 사람이 6명이었습니다(4.5.1절). 실행 결과로 보면, 두 번째 막대 하나로 12개가 7개로 줄었으니 "누적 계산이 의심되면 두 번째 행을 준다"가 효과적인 전략입니다.
